# Frutiger Angler — an Aero gloss and transparency pass

## Goal

Make Frutiger Angler read as glossy Frutiger Aero glass throughout — layered gradients,
translucent panels, specular highlights and soft bloom — instead of the mix of flat fills
and already-decent glass panels it is today.

## Architecture / proposed approach

Everything stays in `vendor/fru-angler/index.html`: the game owns its own `:root` and its own
`<defs>`, and pulling styles in from the site shell would break the isolation that
`tests/angler-look.test.js` enforces with
`assert.deepEqual(files, ['angler.js','fishing.js','index.html','reel.js'])`.

Two changes carry most of the effect. First, a **token refresh** — adopt the site's
`--glass-*`, `--sheen`, `--hairline`, `--radius*` and `--shadow-*` naming so the game has
ready-made Aero recipes rather than hand-writing `rgba()` at every site. Second, and the
biggest win, **gradients inside the scene SVG** — the water, shore, wood, angler and rod all
become gradient-filled, with radial speculars, so the largest surface on screen stops being
flat. `fishing.js`'s `fishSvg()` already uses a gradient body, a radial gloss and a belly
highlight, so the catch card needs far less work than the scene does.

**Rules that must hold throughout, because tests enforce them:** no pixel-palette values
(`#00a2e8`, `#3f48cc`, `#b97a57`), no `shape-rendering: crispEdges`, no class declared twice
as a plain selector, and every new `url(#id)` inside the SVG must resolve to a `<defs>` id in
the same file.

## Risks, tradeoffs, and open questions

**Risks**

1. **`paintRod()` fights CSS.** It writes `stroke` and `fill` inline on `#rod-shaft` and
   `#rod-tip` every time a rod is equipped. Inline attributes beat stylesheet rules, so any
   gradient aimed at the rod from CSS will be silently ignored — and has been, which is why
   `.scene__rod` and `.scene__lure` can look flat without any test failing. Task 6 leaves
   those alone deliberately. If the rod should also be gradient-filled, that belongs in
   `ROD_ART` in `fishing.js`, not in CSS.
2. **The sheen animation is the only perpetual motion in the game.** Bubbles and the drift
   both respect `prefers-reduced-motion`, but a looping animation over a play area is the
   kind of thing that reads as cheap. If it does, drop `animation` from `.lake::after` and
   keep the static highlight.
3. **`.message` covers the entire lake.** Giving it a gradient risks drawing a visible box
   across the whole play area. The replacement in Task 4 fades in from transparent for
   exactly this reason; check it.
4. **More glass means less contrast.** Frosted panels over a busy gradient scene can push
   body text below readable contrast. `scripts/check-contrast.mjs` only checks the *site*
   themes, not the game's hard-coded panel colours, so nothing will catch this. The HUD and
   shop text are the risk.
5. **`backdrop-filter` is expensive.** Six instances already exist; Task 5 adds a full-lake
   gradient underneath them. On a low-end machine the game may stutter while the bobber
   animates. The `--glass` opacity is a dial if it does.
6. **This is the sixth cache-stamp bump.** Task 10 is not optional. `tests/cache-stamps.test.js`
   enforces alignment but cannot catch a forgotten bump — it checks consistency, not
   currency.

**Tradeoffs**

- **Tokens over literals.** Task 2 replaces hard-coded `rgba()` with tokens, so this commit
  looks larger than the visual change. It makes every later edit a one-line change instead
  of hunting for a magic value, and matches how `styles.css` is already written.
- **Gradients in SVG versus CSS.** Filling the scene with `<linearGradient>` rather than CSS
  gradients keeps the art in one place and lets `preserveAspectRatio="none"` stretch it
  without distortion. It does mean a gradient id per surface, all in one `<defs>`.
- **Skipping the site's scenery.** The site shell has bubbles, hills and a sun in
  `styles.css`. The game cannot use them without breaking its isolation, so Task 9's bubbles
  are its own. The two will not animate in sync, which is invisible in practice since they
  are never on screen together.

**Open questions**

1. **How much glass?** Frutiger Aero in full has bubbles, hills, a sun and heavy frosting.
   This plan adds glass, gradients, speculars and bubbles. Hills and grass are not included —
   the lake scene already has a far shore doing that job. Worth asking whether the scene
   wants more landscape.
2. **Should the reel panel keep its heavy blur?** It is the one surface that genuinely needs
   to separate from the busy scene behind it. Reducing it for consistency would hurt
   legibility during the hardest moment of play.
3. **Dark Aero theme.** The game hard-codes its colours and does not follow the site's theme
   toggle, because it is a separate document. So the game's Aero look is fixed while the
   site around it changes. That was a deliberate trade from the original build; revisiting it
   means passing a theme name into the iframe and adding a `[data-theme]` block per theme.
4. **Animation budget.** Five bubbles plus a sheen drift plus the existing splash, bobber
   transition, SHAKE pulse and catch pop. That is six concurrent animations on a small game
   canvas. If it feels busy, the bubbles are the first thing to cut.
